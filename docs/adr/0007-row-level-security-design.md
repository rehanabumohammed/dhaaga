# ADR-0007 · How row-level security is built

**Status** Accepted · P0 WP-3 · 26 Aug 2026

## Context
Supabase exposes every table in the `public` schema through PostgREST, reached
with a publishable key that ships inside the app. Isolation therefore cannot be
an application concern: whatever the client does or fails to do, the database
must refuse rows the caller is not entitled to (AP-5, BR-17).

Three design questions had to be settled.

## Decisions

### 1. The tenant is derived from the user's row, not read from a token claim
`app.current_business_id()` looks the caller's `business_id` up in `app_user`
rather than reading a `business_id` claim from the JWT. A claim is data supplied
by whoever minted the token; a row is data we control. The function is
`SECURITY DEFINER` with a pinned `search_path`, because the tables it reads are
themselves protected by policies that depend on its answer — without that it
would recurse.

The cost is a lookup per policy evaluation. It is a primary-key hit on a small
table, cached within a statement, and it buys an isolation guarantee that does
not depend on token minting being correct forever.

### 2. Policies are generated by a loop, not written out 88 times
A hand-written list of tables is a list somebody forgets to add to. The
migration iterates every table in `public`, picks the business-scoped or
branch-scoped predicate by whether the table has a `branch_id` column, and
creates one `FOR ALL` policy with matching `USING` and `WITH CHECK` clauses.

The risk of generation is that it silently misses something. That risk is
answered by coverage assertions in the isolation suite: any table without RLS
enabled, or without a policy, fails the build **by name**. Both failure modes
were demonstrated deliberately before this ADR was written.

### 3. The suite runs as `authenticated`, not as the owner
A table owner bypasses row-level security. A suite run as the owner would pass
against a completely unprotected database. Every isolation assertion therefore
runs after `set local role authenticated` — the role Supabase's REST layer
actually connects as — with the session's JWT claims set to the user under test.

## Consequences
* An unauthenticated call, or one carrying only a publishable key, reaches
  nothing at all: `anon` holds no privilege on any table.
* Revoking a branch grant takes effect on the caller's next statement. There is
  no session to expire and no cache to invalidate.
* `audit_event` is protected twice over: no update or delete policy exists, and
  those privileges are revoked from `authenticated` as well. Either alone would
  do; both together mean a future migration that accidentally adds a permissive
  policy still cannot open the hole.
* Permission-level rules — who may discount, who may reverse a payment — are
  **not** here. This layer decides which rows exist for a caller; WP-7 decides
  what they may do with them. Conflating the two would make both harder to test.
