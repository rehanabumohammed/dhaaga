## On the keys

The **publishable key is not a secret.** It is compiled into the mobile and web
clients and is visible to anyone who has the app. It is committed here
deliberately. Its safety depends entirely on row-level security: with policies in
place it can only reach rows the signed-in user is entitled to; without them it
can reach everything.

Two credentials must **never** appear in this repository, in a chat, or in a
build log:

* the **service_role / secret key** — it bypasses row-level security completely;
* the **database password** — it is full superuser access to the data.

If either is ever exposed, rotate it in the Supabase dashboard immediately.
Neither is needed by this repository: migrations are pushed with the Supabase
CLI, which prompts for the database password locally and never transmits it
anywhere else.

## Who can run the deployment

**Not the development environment.** It has no network route to Supabase — the
project URL, the REST endpoint, the management API and the database port are all
unreachable from it. The Supabase CLI installs there but cannot log in, link or
push. Deployment therefore runs on the Product Owner's machine, and its output
is reported back.

Two credentials make this unavoidable rather than merely inconvenient:
`supabase login` needs an account token, and `supabase link` needs the database
password. Neither may be shared, so neither can be automated from elsewhere.

## Deployment runbook

Run from the repository root, on the machine that holds the credentials.

```bash
# 0 · confirm the schema is the one that passed
python3 scripts/migrate.py verify
python3 scripts/test.py                      # expect 180 assertions, 0 failures

# 1 · one-time setup
npm install -g supabase
supabase login                               # opens a browser
supabase link --project-ref rnkazgaixjgdzzaebqyv    # prompts for the DB password

# 2 · confirm the link points where you think it does BEFORE pushing
supabase projects list                       # the linked project is marked

# 3 · generate the CLI layout and push
python3 scripts/export_supabase.py
supabase db push

# 4 · verify the cloud database, not the local one
#     DB_URL is the project's connection string from Settings > Database.
#     It contains the password: keep it out of shell history and out of chats.
export DHAAGA_DB_URL='<cloud connection string>'
psql "$DHAAGA_DB_URL" -f db/verify/cloud_postcheck.sql
python3 scripts/test.py isolation

# 5 · put the local URL back so later work does not run against the cloud
export DHAAGA_DB_URL=postgres://postgres@127.0.0.1:5433/dhaaga_dev
```

### If the push fails partway

**Do not walk away from a partial push.** Migrations `0001`–`0008` create the
tables; `0009` applies row-level security and `0010` closes the default-privilege
hole. If the push stops between them, every table exists and is reachable by
anyone holding the publishable key.

Recovery: fix the reported error and re-run `supabase db push`, which resumes
from the first unapplied migration. If it cannot be made to succeed promptly,
pause the project in the dashboard rather than leaving it exposed.

### What the post-check proves

`db/verify/cloud_postcheck.sql` returns one row per check with a verdict, FAIL
rows sorted to the top. It compares the cloud database against the verified
local schema: table count, exact table list, a column-level fingerprint, RLS
enabled everywhere, a policy on every table, zero privileges for `anon`,
insert-and-read-only on the audit trail, and the required extensions.

Its expected values are generated by `scripts/gen_cloud_check.py` from the local
schema. Regenerate after any migration, or it will report a false failure.

Running it locally shows exactly one FAIL — `migrations · CLI migration history
present` — because the CLI's history table only exists after a real push. That
is the check working, not a defect.

### Migration bookkeeping: two systems, one source

The cloud project's applied-migration history is kept by the Supabase CLI in
`supabase_migrations.schema_migrations`. The local and CI databases use this
repository's runner and `dhaaga_meta.schema_migration`. Both apply the identical
SQL from `db/migrations`, which stays the single source of truth. Do not point
`scripts/migrate.py` at the cloud project: it would not recognise the CLI's
history and would try to re-apply everything.

`scripts/export_supabase.py` regenerates the CLI's expected layout from
`db/migrations`, which stays the source of truth. The generated directory is
git-ignored: never edit it, and never edit the cloud project by hand — a schema
that exists only in a dashboard is a schema nobody can review or roll back.

## Two open questions before this project takes real data

**1. Which environment is this?** ADR-0001 assumes three: development, staging
and production. One project cannot be all three. Pushing an in-progress P0
schema into what later becomes production means the first real customer record
sits in a database that has been rebuilt several times during development.

Recommendation: treat `rnkazgaixjgdzzaebqyv` as **development/staging** for the
remainder of P0, and create a separate production project before the pilot
branch goes live at the P3 gate. Two projects on the free tier cost nothing and
remove the risk entirely.

**2. Should the seed be loaded?** `db/seed/0001_development_business.sql` creates
a business explicitly named "Dhaaga Tailors (Development)" with placeholder tax
codes and five fictional staff. It belongs in a development project and does not
belong in one that will hold real customers.

If this project is development: load it, and the seed-integrity tests pass.
If it is production: do not, and expect `0009_seed_integrity.sql` to fail there —
which is correct behaviour, not a defect.

## After the first push

1. Confirm the migration list in the dashboard matches `db/migrations`.
2. Run the post-check and the isolation suite against the cloud project.
3. Take a backup and rehearse a restore (WP-10) before any real data exists.
